# Research — `adapt` v2: project integration (Phase 9)

- **Date:** 2026-06-12
- **ROADMAP:** Phase 9 (lines 336–364); Track 2 order 11→8→10→**9**→12
- **Depends on (both merged):** Phase 8 (payload paths, `--project` install), Phase 10 (`render_contract` + `templates/CONTRACT.template.md`)

## The question

`adapt` v1 generates *adapt-owned* harness config (`.codex/config.toml`, `.cursor/rules/*.mdc`,
`opencode.json`, `.claude/settings.json`) from one Markdown source. Phase 9 makes `adapt` deliver
**everything a governed project needs**: artifact scaffolding, the resolved binary wired in, and the
operating **contract** injected into each harness's native always-on surface — *without clobbering
user files*. What in the current design supports that, and what has to change?

## What `adapt` is today (read of `gatekeeper/src/adapt.rs`, 828 LOC)

- **Generation is pure**: each builder is `fn build_<harness>(read_root) -> Result<Vec<GenFile>>`,
  where `GenFile { rel_path, contents }` is a *complete* file.
- **One I/O funnel**: `apply_or_check(files, write_root, check)`. Write mode creates parent dirs and
  writes each file whole. `--check` mode does **exact string equality** against disk → exit `0`
  (up-to-date) / `1` (DRIFT/MISSING) / `2` (write error).
- **Two roots** (`cmd_adapt(args, read_root, write_root)`): `read_root` = framework (skills,
  instincts, AGENTS.md, hook scripts, `templates/`); `write_root` = project. When they **differ**
  (a project install) `cmd_adapt` already appends `build_project_config(write_root)` →
  `.claude/topology/config.toml` (never overwrites). This "roots differ" branch is the natural seam
  for Phase 9.
- **Phase 10 render layer** (already merged): `render_contract(template, ctx)` is pure and
  fail-closed; `project_ctx()` yields `artifacts_root = ".claude/topology"` + the `GATEKEEPER_BIN`
  wiring note. `adapt --contract project` prints it to stdout (no file written) — Phase 9 calls the
  same `render_contract` and *writes* the result.

## The two structural mismatches Phase 9 must resolve

**M1 — `.claude/settings.json` has one writer today, and it clobbers.**
`build_claude` emits the whole `settings.json` (only `hooks`). A project with a pre-existing
`settings.json` (user `permissions`, `model`, `env`, …) is silently overwritten. Phase 9 adds an
`env.GATEKEEPER_BIN` block *and* the spec says **"never clobber user content."** ⇒ settings.json
delivery must become a **JSON merge**: read existing (if any), set `hooks` + `env.GATEKEEPER_BIN`,
preserve every other key. `--check` for it must compare *our* keys, not the whole file (a user
adding a `model` key is not "drift").

**M2 — the contract lands in user-owned files; exact-file diff cannot model that.**
The contract is delivered *append-only, import-first* into files the user owns and edits:
- **Claude Code**: append one line `@.topology/CONTRACT.md` to `<project>/CLAUDE.md` (create the
  file containing just that line if missing). The body lives in `<project>/.topology/CONTRACT.md`
  (rendered via `project_ctx()`), so upgrades never touch the user's `CLAUDE.md`.
- **codex `AGENTS.md`** (no import mechanism): an idempotent **managed block** delimited by
  begin/end markers; re-running updates the block in place; `--check` flags drift in the block only.
- Neither may clobber or regenerate the user's surrounding content.

`apply_or_check`'s byte-equality is wrong for both. ⇒ a **second delivery primitive** is needed:
`ensure_import_line` (presence-or-append, idempotent) and `ensure_managed_block`
(marker-delimited upsert + drift check). These are *partial-file* editors, distinct from the
*whole-file* `GenFile` path.

## Supporting facts

- **Binary path for `GATEKEEPER_BIN`**: the installer places the binary at `$ROOT/bin/gatekeeper`
  and the hooks already resolve `$GATEKEEPER_BIN → $ROOT/bin/gatekeeper → …` (USER-GUIDE binary
  resolution table). So the stable value to write is `<read_root>/bin/gatekeeper` — adapt knows
  `read_root`. `env::current_exe()` is rejected: during install the running binary may be a temp
  download path, not the final `bin/` location.
- **Scaffold dirs**: `.claude/topology/{research,specs,plans,verify,reviews}` — empty dirs. Git
  doesn't track empty dirs; either drop a `.gitkeep` or let the gates `create_dir_all` on first
  write. Open question Q3.
- **`.topology/CONTRACT.md`**: the payload reserves this slot (ADR-0013 / Phase 10 note). For a
  `--project` install the payload is vendored at `<project>/.topology/`, so the import target
  `@.topology/CONTRACT.md` is project-relative and correct. Global-only installs have no project
  `.topology/`; the installer already "prints the command to run inside any project" for global
  scope — so **contract/import delivery is inherently `--project`-scoped** (matches the phase title
  "project integration"). Open question Q4 (global scope) — proposed out of scope.
- **Test conventions** (`tests/cli_adapt.rs`): run the compiled binary in a tempdir, pin
  `TOPOLOGY_ROOT` to the scratch framework (so Phase 11 binary-adjacent resolution doesn't escape to
  the real repo), assert generated files + exit codes. Phase 9 fixtures follow this idiom; the
  "roots differ" project-install fixture (`adapt_writes_to_project_not_framework`) is the template.

## Open questions for the design gate

- **Q1 — settings.json merge depth.** Shallow top-level merge (set `hooks`, `env`; keep other keys),
  or deep-merge into nested `env`? Proposal: shallow at top level, but *merge into* an existing `env`
  object so a user's other env vars survive; `hooks` is adapt-owned and replaced wholesale.
- **Q2 — `--check` for partial-file deliveries.** Define check = "import line present" /
  "managed block present and byte-current"; surrounding user content ignored. Confirm exit-code
  contract reuse (0 clean / 1 drift / 2 error).
- **Q3 — scaffold empty dirs.** `.gitkeep` vs. lazy creation. Proposal: create the dirs (so `doctor`
  and a first session see them) and `.gitkeep` them so they survive commit.
- **Q4 — scope of harnesses this PR.** Full spec lists claude + codex + cursor + opencode + the
  `--init-agent` stretch. Proposal for a reviewable PR: deliver **GATEKEEPER_BIN + scaffold** (all
  project installs), **claude import** and **codex managed block** (both have concrete verify
  criteria in the spec), and the **bare-stub first-session instruction**. Carry **cursor/opencode
  contract-as-native-surface** and **`--init-agent`** (explicitly "Stretch") to a documented
  follow-up. Decide in the spec; flag for maintainer review in the PR.
- **Q5 — first-session init instruction.** Where does the "bare stub → write project docs above the
  import → then proceed" gate-shaped instruction live: in the rendered `CONTRACT.md`, or the
  `_getting-started` skill? Proposal: in `CONTRACT.md` (it's the always-loaded surface), guarded so
  it only fires when the project doc above the import is an empty/stub.

## Reproduction of the gap (verify-gate seed)

On `main`, `adapt --harness claude` in a project with a pre-existing `.claude/settings.json`
overwrites it (M1), and never appends an `@.topology/CONTRACT.md` import to `CLAUDE.md` nor sets
`GATEKEEPER_BIN` (the deliverables don't exist). The verify artifact will reproduce-then-resolve
each spec acceptance bullet (append-only import, no-op second run, codex block round-trip,
GATEKEEPER_BIN bare invocation, bare-stub instruction).
