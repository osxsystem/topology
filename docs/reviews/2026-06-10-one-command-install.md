## Non-blocking notes
- README.md (doctor paragraph, "the full resolution order: `$GATEKEEPER_BIN` → `bin/` → plugin data → repo build → `PATH`") overclaims doctor's transparency: `gatekeeper/src/doctor.rs:35-66` probes only `$GATEKEEPER_BIN`, PATH, and the repo build — there is no probe line for `$ROOT/bin/gatekeeper` or `$CLAUDE_PLUGIN_DATA/bin/gatekeeper`, the two tiers that now outrank the repo build. After a prebuilt-only install, doctor prints "repo build: not found" and never lists the actual highest-priority binary location (the static `resolution split:` sentence at doctor.rs:66-69 does name the tiers, and the `binary:` self-path line partially compensates when doctor is run via the installed binary). Extending the probes was arguably out of scope (spec non-goal: no Rust behavior change), so the fix belongs in the README wording.
- scripts/install.sh:106 — the chmod manifest entry is a relative glob (`hooks/*.sh scripts/*.sh (made executable)`), not absolute paths. Spec §5 says "the manifest as absolute paths"; plan task 6 explicitly sanctioned the one-line summary form, and all *created* files (binary, CLAUDE.md, pre-commit) are absolute (verified live), so AC-5's letter is satisfied — but the modified-files entry deviates from the spec's absolute-paths wording.
- scripts/fetch-gatekeeper.sh:108 — the final `mv` from the `mktemp -d` workspace to `<dest-dir>` typically crosses filesystems, so it is a copy, not the "atomic mv" the spec §3 claims. The window opens only after checksum + smoke verification, so the worst case is a truncated `bin/gatekeeper` on a crash mid-copy; consequence is a re-run, not a security hole.
- scripts/fetch-gatekeeper.sh:86 — `grep "$ASSET_NAME"` over SHA256SUMS is unanchored. Unambiguous for the four real asset names, and a hypothetical multi-line match fails closed in `shasum -c` (missing file → non-zero), but `grep -E "[[:space:]]${ASSET_NAME}\$"` would be precise.
- scripts/install.sh piped mode executes statements as bash streams them from stdin; no command in the script reads stdin (verified end-to-end), but the conventional `main "$@"` wrapper that guards against partial-download execution of `curl | bash` installers is absent.
- scripts/install.sh:56-68 — if `$ROOT/bin/gatekeeper` already exists from a prior run and the fetch fails, the stale binary is silently accepted (the `[[ ! -x "$BIN" ]]` fallback check at line 65 passes) without appearing in the manifest. Acceptable for re-runs, but a "using existing binary" line would be more honest.
- Security-floor observation, not a weakening: `$ROOT/bin/gatekeeper` now outranks the repo build in security-scan.sh:29-32, and neither `bin/` nor `scripts/fetch-gatekeeper.sh` is covered by `tamper-security-wiring` (security/rules.toml:122) or `protected_paths` (security/rules.toml:150). The previously-preferred `gatekeeper/target/release/gatekeeper` was equally writable, `bin/` is gitignored so pre-commit integrity cannot apply, and ADR-0011 §4 states the threat boundary (mistakes, not a determined evader) — consistent with the repo's documented model.
- hooks/ensure-gatekeeper.sh:15 uses `set -euo pipefail` alongside the "never exits non-zero" contract; every reachable branch is guarded (all three terminal paths observed exiting 0), but an unexpected failure in an unguarded command (e.g. the `cd` inside the HOOK_DIR assignment, line 17) would exit non-zero. Practically negligible.
- docs/verify/2026-06-10-one-command-install.md AC-5 honestly discloses that the fresh-clone-from-GitHub leg cannot exercise the new fetch helper pre-merge; the live curl one-liner remains unproven until `v0.2.0` is tagged. The cargo fallback and the failure message cover the gap, per spec §6.
- gatekeeper/src/doctor.rs:35 retains the now-doubly-stale comment "neither hook reads it yet" about `$GATEKEEPER_BIN` — pre-existing, correctly left untouched per diff traceability; mentioning, not counting.
